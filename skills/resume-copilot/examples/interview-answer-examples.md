# 面试参考答案规则与示例

仅在用户明确要求附答案时读取。本文件既定义 **Generated Reference Answer 的可见写作质量**，也提供 Gold Answer 示例。

示例不是用户项目的事实来源，不得把其中的项目、技术栈、数字或结论迁移到其他用户项目。生成答案时仍以 Career Profile、Repository Evidence 与当前问题为准。

外层仍可保留 `**直接回答**` 与 `**展开说明**` 两部分，以对应内部 `overview` / `principleDetail`；但这只是外层组织，不代表所有答案都要写成两个大段。`展开说明` 必须根据知识本身选择最适合的结构：执行链用步骤或时序，比较题用表格，状态变化用流程图，抽象机制用分层解释。

---

## Answer Quality Contract（硬约束）

### 1. 当前答案必须先自洽，再生成 Follow-up

Follow-up Question 用于进一步深化、验证或扩展当前答案，**不得承担“补完上一题本来就应该解释清楚的核心机制”的职责**。

在从当前 Answer 抽取下一层 Node 前，先检查：如果读者只看这一题，是否已经能理解“结论为什么成立、关键步骤怎么走、项目实际做到哪里”。如果不能，先补当前答案，再做 Node Extraction。

### 2. Why-Layer Rule：不能只写“项目怎么做”

对于架构、机制、数据模型、并发、一致性、Agent、检索、测试设计等非纯事实问题，仅说明代码做了什么不算完整。

当问题存在明确设计动机时，答案应继续解释：

- 为什么需要这一层设计；
- 它解决的核心矛盾是什么；
- 如果删除或替换这一层，会出现什么问题；
- 它对应什么通用工程原则。

不要机械地给所有题都补“为什么”。纯事实题、命令说明题、简单定义题没有必要强行扩展。

### 3. Knowledge Abstraction Rule：从项目事实抽象出可迁移知识

当项目实现体现了可复用的通用技术概念时，在 Project Grounding 之后应再抽象一层知识模型，帮助候选人把“这个项目这么写”升级成“我理解这类问题为什么这么设计”。

例如：

```text
import.meta.url vs process.cwd()
→ module-relative resource vs workspace-relative resource

Schema + ID Check + Evidence Rule
→ structural validity vs referential integrity vs semantic validity

temp + rename + lock
→ preparation / atomic visibility / critical section
```

抽象层属于技术理解，不得反向伪装成仓库已实现的项目事实。

### 4. No Terminology-as-Explanation Rule

不得用一个技术名词替代机制解释。

以下答案都不完整：

```text
“通过 Outbox 保证可靠性。”
“通过 MVCC 保证一致性。”
“通过 Checkpoint 实现恢复。”
“通过 Redis 做分布式协调。”
“通过 Reranker 提升检索效果。”
```

一旦关键结论依赖某个技术机制，当前答案至少继续解释：

- 该机制实际保存 / 比较 / 更新 / 传递什么；
- 哪一步使目标性质成立；
- 在什么条件下会失效或需要额外保护。

### 5. Mechanism Chain：机制题必须能被逐步推演

机制 / 实现类问题优先形成下面这条链：

```text
输入 / 前提
→ 关键参与者
→ 执行步骤
→ 状态变化
→ 为什么结果成立
→ 失败边界 / 取舍
```

不要求把这些词作为标题展示，但答案内容必须覆盖本题真正依赖的部分。

只罗列组件名不算机制。例如：

```text
PostgreSQL + Redis + SSE + Outbox
```

不是一条完整解释；必须说明它们之间谁先写、谁后发、状态在哪里持久化、连接断开后为什么任务仍然存在。

### 6. Concrete Walkthrough：抽象机制尽量落到一个具体例子

当问题涉及流程、竞态、状态机、解析、安全边界、测试判断或恢复时，至少给一个可以自己走完的例子：

- A / B 两个并发 Worker 的时间线；
- 一条任务从 `submitted → working → completed` 的状态变化；
- 一份输入数据经过解析、校验、持久化的过程；
- 一段最小伪代码；
- 一张简短流程图。

例子的目的不是凑篇幅，而是让“为什么成立”可以被验证。

### 7. Adaptive Structure：按知识结构组织，不按固定模板堆字

外层可以保留 `直接回答 / 展开说明`，但 `展开说明` 内部必须按问题选择结构：

- **执行过程 / 调用链** → 编号步骤、时序或流程图；
- **多个方案区别** → 对比表格；
- **抽象概念分层** → 分层模型或短列表；
- **并发 / 一致性** → 时间线 + 原子点；
- **状态恢复** → 状态机 + 持久化位置；
- **简单定义** → 两三个自然段即可。

不要为了“看起来有结构”机械堆小标题，也不要把所有内容压进一个高密度自然段。

### 8. CURRENT / PRINCIPLE / IMPROVEMENT 边界

答案需要始终分清三类内容：

- `CURRENT`：仓库 / Career Profile 可以证明当前已经实现；
- `PRINCIPLE`：通用技术原理，可以完整解释但不代表项目已落地；
- `IMPROVEMENT`：如果改造会怎么做，必须使用假设语气。

不必把三个标签原样显示出来，但语义边界必须清楚。

## Gold Answer 1：解释现有实现及失败边界

### 问题：已有目录时为什么要求 `--force`？它能保证安装安全吗？

**直接回答**

`--force` 解决的是覆盖意图，不保证安装过程安全。当前 CLI 发现目标目录已存在时默认拒绝安装；用户显式传入 `--force` 后才会覆盖。但覆盖是“删除旧目录，再复制新目录”，所以中途失败仍可能让旧版本丢失。

**展开说明**

这里要区分两个不同问题：**是否允许覆盖**，以及**覆盖过程中能否保持一致状态**。

当前安装顺序是：

```text
检查目标存在
→ 检查 --force
→ 删除旧目录
→ 复制新目录
```

`--force` 只作用在第二步：它证明用户明确同意覆盖旧目录。真正的数据一致性风险发生在后两步之间。

例如旧版本已经删除，新版复制到 60% 时磁盘满了，最终目录只剩一半新版文件。此时 `--force` 已经正确完成“显式授权覆盖”的职责，但系统没有旧版本、也没有完整新版。

所以这里可以抽象成两个工程概念：

| 问题 | 当前机制 |
| --- | --- |
| 覆盖是否经过用户明确授权 | `--force` |
| 更新失败时是否仍有完整版本可用 | 当前未保证 |

因此准确表述是：`--force` 是 **overwrite guard**，不是 transaction，也不是 atomic install。

## Gold Answer 2：推演尚未实现的改造方案

### 问题：如果要避免覆盖中途把旧版删掉，你会怎样改安装流程？

**直接回答**

如果改造，我会采用“先准备、再切换、最后清理”的流程：先在临时目录完整复制并校验新版，成功后再切换正式目录。这样准备阶段失败时，旧版本仍然可用。

**展开说明**

核心不是简单增加一个 `temp` 目录，而是把更新拆成 **Preparation → Visibility Switch → Recovery** 三个阶段。

1. **Preparation**：在目标同一文件系统中创建唯一临时目录，把新版完整复制进去并校验。
2. **Visibility Switch**：把旧 `target` 重命名为 `backup`，再把 `temp` 重命名为正式 `target`。
3. **Recovery / Cleanup**：切换成功后删除 `backup`；如果第二次 rename 失败，则优先尝试恢复旧版。

为什么临时目录最好和目标在同一文件系统？因为跨文件系统 rename 可能退化成复制 + 删除，失去单次 rename 的原子可见性。

但这仍不能宣称“整个更新是原子的”。因为：

```text
rename(target, backup)
rename(temp, target)
```

是两次独立操作。

例如进程恰好在第一次 rename 后崩溃，下次启动可能看到：

```text
target  不存在
backup  存在
temp    存在
```

这说明系统处于一个可识别的中间状态。恢复逻辑应该根据状态决定回滚旧版还是继续提交，而不是直接清理 `backup`。

这类设计背后的通用原则是：**先准备不可见的新状态，再做尽量短的可见性切换，并让所有中间状态都可恢复。** 当前项目尚未实现这套协议，所以必须用“如果改造，我会”来描述。

## Gold Answer 3：说明测试结果的实际证明范围

### 问题：自动化检查全绿，为什么仍可能有用户可见错误？

**直接回答**

检查全绿只能说明现有测试观察到的条件成立。只要输入场景、观察点或判断标准没有覆盖用户实际看到的结果，页面依然可能出错。

**展开说明**

可以把一个测试理解成：

```text
输入
→ 被测系统
→ Observation Point
→ Assertion
```

测试是否有价值，不只取决于断言数量，还取决于 **Observation Point 是否落在真正要保证的结果上**。

以主题配色为例，如果测试只断言生成的 HTML 包含：

```css
--brand: ...;
```

即使 CSS 中定义了这个变量、却没有任何实际选择器使用它，测试仍然会通过；用户在浏览器里看到的颜色却可能完全没变化。

因此这里存在两个层级：

| 层级 | 能证明什么 |
| --- | --- |
| 静态生成物检查 | 文件里出现了预期字符串 / 结构 |
| 浏览器行为检查 | 浏览器解析、层叠、布局后用户实际看到预期结果 |

如果目标 Claim 是“生成文件包含正确主题变量”，前者足够；如果 Claim 是“用户看到正确主题效果”，就需要把观察点移动到浏览器 computed style 或真实截图 / 打印结果。

通用原则是：**测试结论不能超过测试的输入范围、观察点和判定标准。**

## Gold Answer 4：从项目路径实现抽象出通用知识

### 问题：既然目标目录按当前工作目录解析，为什么源目录不能也用 `process.cwd()`？

**直接回答**

因为源目录和目标目录表达的是两种不同的路径语义。源目录属于已经安装的 npm 包，应该跟着模块自身位置走；目标目录属于用户当前运行命令的项目，才应该跟着 `process.cwd()` 走。

**展开说明**

项目里这两个路径分别回答两个问题：

```text
源目录：这个 CLI 自己安装在哪里？
目标目录：用户现在在哪个项目里执行命令？
```

所以源路径适合从 `import.meta.url` 推导：

```text
import.meta.url
→ fileURLToPath
→ dirname
→ packageRoot
→ skillsRoot
```

目标路径则适合：

```text
process.cwd()
→ path.resolve(cwd, target)
```

假设 npm 包实际安装在：

```text
/opt/fish-skill
```

用户在：

```text
/home/me/app
```

执行安装命令。

那么正确语义是：

```text
source = /opt/fish-skill/skills/resume-copilot
 target = /home/me/app/.agents/skills/resume-copilot
```

如果源目录也从 `cwd` 推导，CLI 就会去 `/home/me/app/skills` 找自己的包内资源；用户换一个执行目录，源文件位置也跟着“漂移”，这显然不符合包资源的语义。

这里可以进一步抽象成一个通用模型：

| 路径类型 | 参照物 | 常见来源 |
| --- | --- | --- |
| Module-relative Resource | 程序 / 包自身位置 | `import.meta.url`、`__dirname` |
| Workspace-relative Resource | 当前运行项目 / 工作目录 | `process.cwd()` |

因此这道题不只是 Node.js API 的区别，而是**资源归属决定路径参照系**：包内静态资源跟模块走，用户工作区资源跟执行上下文走。

## Gold Answer 5：从三种校验抽象出三层正确性

### 问题：JSON Schema 已经规定字段了，为什么还需要引用检查和证据规则？

**直接回答**

因为它们验证的是三种不同层级的正确性。Schema 只能证明“数据长得合法”；引用检查证明“引用的对象真实存在”；证据规则再判断“这些存在的事实是否真的足以支撑最终 Claim”。

**展开说明**

可以把整个验证链抽象成：

```text
Structural Validity
        ↓
Referential Integrity
        ↓
Semantic Evidence
```

具体来看：

| 层级 | 典型问题 | 例子 |
| --- | --- | --- |
| Structural Validity | 字段、类型、枚举是否合法 | `claimIds` 是否为非空字符串数组 |
| Referential Integrity | ID 指向的对象是否存在 | `claim-cli` 是否真的存在 |
| Semantic Evidence | 事实是否足以推出这句话 | CLI 代码能否支撑“我独立开发” |

例如：

```json
{
  "claimIds": ["claim-does-not-exist"]
}
```

从 Schema 角度它完全可能合法：字段存在、类型正确、数组非空。但如果 Claims 集合里根本没有这个 ID，关系就断了，所以需要跨对象引用检查。

再进一步，即使 `claim-cli` 存在，它引用的事实只有“仓库实现了 install 命令”，这也不能自动推出“我独立开发了 install”。要支持 ownership 表述，还需要用户确认或其他 ownership 证据。

所以这三层不能互相替代：

```text
Schema 正确
≠ 引用一定存在
≠ 语义一定可信
```

这个设计的 Why Layer 是：**把数据结构、对象关系和业务语义分开验证，才能知道错误到底发生在哪一层，也避免把“格式正确”误当成“内容可信”。**
