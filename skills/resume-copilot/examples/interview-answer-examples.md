# 面试参考答案示例

仅当用户明确要求附答案时读取。

本文件只展示 `policies/interview-depth-policy.md` 中规则的落地方式，**不新增硬规则**。示例不是用户项目事实来源，不得复制其中的技术栈、数字、实现或 Ownership 到其他项目。

外层统一展示 `**直接回答**` 与 `**展开说明**`；内部结构按问题选择，不要求两个大段。

## 示例 1：区分当前实现与失败边界

### 问题：已有目录时为什么要求 `--force`？它能保证安装安全吗？

**直接回答**

`--force` 解决的是覆盖意图，不保证安装过程安全。当前 CLI 发现目标目录已存在时默认拒绝；显式传入 `--force` 后才允许覆盖。但当前覆盖顺序是先删除旧目录再复制新版，所以复制中途失败仍可能留下半套文件。

**展开说明**

这里有两个不同问题：**是否允许覆盖**，以及**更新过程中是否始终保持一套完整版本**。

```text
检查目标存在
→ 检查 --force
→ 删除旧目录
→ 复制新目录
```

`--force` 只解决第二步的授权问题。假设旧版本已经删除，新版复制到 60% 时磁盘满了，最终目录里既没有旧版，也没有完整新版。

所以可以抽象成：

| 问题 | 当前机制 |
| --- | --- |
| 用户是否明确同意覆盖 | `--force` |
| 更新失败后是否仍有完整版本 | 当前未保证 |

因此 `--force` 是 overwrite guard，不是 transaction，也不是 atomic install。

## 示例 2：推演尚未实现的改造方案

### 问题：如果要避免覆盖中途把旧版删掉，你会怎样改安装流程？

**直接回答**

如果改造，我会采用“先准备、再切换、最后清理”的流程：先在临时目录完整复制并校验新版，成功后再切换正式目录。这样准备阶段失败时旧版仍然可用。

**展开说明**

核心可以分成三个阶段：

1. **Preparation**：在目标同一文件系统中创建唯一临时目录，完整复制并校验新版。
2. **Visibility Switch**：把旧 `target` 重命名为 `backup`，再把 `temp` 重命名为 `target`。
3. **Recovery / Cleanup**：成功后清理 `backup`；第二次 rename 失败时优先恢复旧版。

临时目录与目标放在同一文件系统，是为了保留单次 rename 的原子可见性。但：

```text
rename(target, backup)
rename(temp, target)
```

仍是两次独立操作，不能说整条流程完全原子。

例如进程在第一次 rename 后崩溃，下次启动可能看到：

```text
target  不存在
backup  存在
temp    存在
```

恢复逻辑需要识别这个中间状态，再决定恢复旧版还是继续提交。

通用工程原则是：**先准备不可见的新状态，再做尽量短的可见性切换，并让每个中间状态都可恢复。** 当前项目若尚未实现，就必须保持“如果改造，我会”的假设语气。

## 示例 3：从项目实现抽象成通用知识

### 问题：既然目标目录按当前工作目录解析，为什么源目录不能也用 `process.cwd()`？

**直接回答**

因为源目录和目标目录表达的是两种路径语义。源目录属于已经安装的 npm 包，应该跟模块自身位置走；目标目录属于用户当前执行命令的项目，才应该跟 `process.cwd()` 走。

**展开说明**

两个路径分别回答：

```text
源目录：这个 CLI 自己安装在哪里？
目标目录：用户现在在哪个工作区运行命令？
```

因此源目录适合：

```text
import.meta.url
→ fileURLToPath
→ dirname
→ packageRoot
→ skillsRoot
```

目标目录适合：

```text
process.cwd()
→ path.resolve(cwd, target)
```

假设包在 `/opt/fish-skill`，用户在 `/home/me/app` 中执行：

```text
source = /opt/fish-skill/skills/resume-copilot
target = /home/me/app/.agents/skills/resume-copilot
```

如果源也从 `cwd` 推导，CLI 会错误地去 `/home/me/app/skills` 找自己的包资源。

这可以进一步抽象成：

| 路径类型 | 参照物 | 常见来源 |
| --- | --- | --- |
| Module-relative Resource | 程序 / 包自身位置 | `import.meta.url`、`__dirname` |
| Workspace-relative Resource | 当前工作目录 | `process.cwd()` |

本质是：**资源归属决定路径参照系。**

## 示例 4：把多层校验讲成一个知识模型

### 问题：JSON Schema 已经规定字段了，为什么还需要引用检查和证据规则？

**直接回答**

因为它们验证的是三种不同层级的正确性。Schema 证明数据形状合法；引用检查证明对象关系没有悬空；证据规则再判断这些事实是否真的足以支撑最终 Claim。

**展开说明**

可以抽象成：

```text
Structural Validity
        ↓
Referential Integrity
        ↓
Semantic Evidence
```

| 层级 | 典型问题 | 示例 |
| --- | --- | --- |
| Structural Validity | 字段、类型、枚举是否合法 | `claimIds` 是否为非空字符串数组 |
| Referential Integrity | 引用对象是否存在 | `claim-cli` 是否真实存在 |
| Semantic Evidence | 事实是否足以推出表述 | CLI 代码能否支撑“我独立开发” |

例如：

```json
{
  "claimIds": ["claim-does-not-exist"]
}
```

它的 JSON 形状完全可以合法，但如果 Claims 集合中没有这个 ID，引用关系仍然断了。

再进一步，即使 `claim-cli` 存在，若它只证明“项目实现了 install”，也不能自动推出“用户独立开发了 install”；Ownership 还需要人物事实支撑。

所以：

```text
Schema 正确
≠ 引用一定存在
≠ 语义一定可信
```

Why Layer 是：把数据结构、对象关系、业务语义分开验证，才能准确知道错误发生在哪一层，也避免把“格式正确”误当成“内容可信”。

## 示例 5：测试为什么全绿仍可能有用户可见错误

### 问题：自动化检查全绿，为什么仍可能有用户可见错误？

**直接回答**

测试全绿只能说明现有测试观察到的条件成立。如果输入场景、观察点或判定标准没有覆盖用户真正看到的结果，页面仍然可能出错。

**展开说明**

可以把测试理解成：

```text
输入
→ 被测系统
→ Observation Point
→ Assertion
```

假设测试只检查生成的 HTML 里存在：

```css
--brand: ...;
```

即使变量从未被任何实际选择器使用，这个静态断言仍然会通过，但用户看到的颜色可能完全没有变化。

因此：

| 层级 | 能证明什么 |
| --- | --- |
| 静态生成物检查 | 文件里出现预期字符串 / 结构 |
| 浏览器行为检查 | 浏览器解析与布局后用户实际看到预期结果 |

如果 Claim 是“生成文件包含主题变量”，前者足够；如果 Claim 是“用户看到正确主题”，观察点就应该移到 computed style、真实截图或打印结果。

通用原则是：**测试结论不能超过测试的输入范围、观察点和判定标准。**
