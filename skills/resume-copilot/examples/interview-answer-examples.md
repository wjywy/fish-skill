# 面试参考答案示例

本文件只展示 `policies/interview-depth-policy.md` 中规则的落地方式，**不新增硬规则**。示例不是用户项目事实来源，不得复制其中的技术栈、数字、实现或 Ownership 到其他项目。

共同特点：

- 每个 Question 一旦被物化，就直接给完整 DEEP_STUDY 答案；
- 开头自然回答问题，但不固定显示 `直接回答 / 展开说明`；
- 结构由问题本身决定；
- Follow-up 只负责进一步深化，不负责补完当前题。

## 示例 1：机制 / 失败边界题

### 问题：已有目录时为什么要求 `--force`？它能保证安装安全吗？

`--force` 解决的是“用户是否明确允许覆盖”，不保证覆盖过程本身安全。当前 CLI 在目标目录存在时默认拒绝；显式传入 `--force` 后才允许继续。但当前顺序是先删除旧目录再复制新版，因此复制中途失败时仍可能留下半套文件。

当前链路是：

```text
检查目标存在
→ 检查 --force
→ 删除旧目录
→ 复制新目录
```

这里其实有三种不同性质：

| 性质 | 当前是否具备 | 原因 |
| --- | --- | --- |
| 覆盖意图保护 | 有 | 已存在时必须显式传 `--force` |
| 失败后保留旧版 | 没有 | 删除发生在复制之前 |
| 整次更新原子可见 | 没有 | 删除与逐文件复制是多个独立操作 |

例如新版复制到 60% 时磁盘写满，用户虽然确实授权了覆盖，但旧版已经被删除，新版又不完整。因此 `--force` 是 overwrite guard，不是 transaction，也不是 atomic install。

## 示例 2：改造 / 恢复题

### 问题：如果要避免覆盖中途把旧版删掉，你会怎样改安装流程？

如果改造，我会采用“先准备、再切换、最后清理”的流程：先在临时目录完整复制并校验新版，准备成功后再切换正式路径。这样准备阶段失败时，旧版本仍然可用。

可以把更新拆成三个阶段：

1. **Preparation**：在目标同一文件系统创建唯一临时目录，完整复制并校验新版。
2. **Visibility Switch**：把旧 `target` 重命名为 `backup`，再把 `temp` 重命名为 `target`。
3. **Recovery / Cleanup**：切换成功后删除 `backup`；第二次 rename 失败时优先恢复旧版。

为什么强调“同一文件系统”？因为单次 rename 在同一文件系统内通常具有原子可见性；跨文件系统可能退化成复制 + 删除。

但：

```text
rename(target, backup)
rename(temp, target)
```

仍是两次独立操作。进程若在两次 rename 之间崩溃，下一次启动可能看到：

```text
target  不存在
backup  存在
temp    存在
```

所以恢复逻辑必须把这些中间状态当作协议的一部分，而不是把残留目录都当垃圾清理。通用原则是：**先准备不可见的新状态，再做尽量短的可见性切换，并让所有中间状态可识别、可恢复。**

## 示例 3：对比 / 分层题

### 问题：JSON Schema 已经规定字段了，为什么还需要引用检查和证据规则？

不能把三者当成同一种校验，因为它们验证的是三层不同的正确性：Schema 只保证数据形状合法；引用检查保证对象关系没有悬空；证据规则再判断这些事实是否真的足以支撑最终 Claim。

| 层级 | 判断什么 | 一个反例 |
| --- | --- | --- |
| Structural Validity | 字段、类型、枚举是否合法 | `claimIds` 写成数字 |
| Referential Integrity | 引用对象是否存在 | bullet 指向不存在的 Claim |
| Semantic Evidence | 事实是否足以支撑表述 | 只有仓库代码却写“我主导” |

例如：

```json
{
  "claimIds": ["claim-does-not-exist"]
}
```

它完全可能通过 JSON Schema，因为字段存在、类型也正确，但业务引用仍然是坏的。

再进一步，即使 `claim-cli` 确实存在，如果它只证明“项目实现了 install”，也不能自动推出“用户独立开发了 install”；Ownership 还需要人物事实支撑。

所以：

```text
Schema 正确
≠ 引用一定存在
≠ 语义一定可信
```

这类问题最适合直接用“分层模型 + 反例”解释，而不是先写一段 summary 再重复展开。

## 示例 4：并发题

### 问题：两个 Worker 并发消费同一事件时，“先查再写”为什么仍可能重复执行？

因为“查询是否处理过”和“写入处理结果”不是一个原子操作。两个事务可以在写入之前都看到“未处理”，然后各自继续执行副作用。

可以直接按时间线推演：

```text
T1  Worker A: SELECT eventId → 未处理
T2  Worker B: SELECT eventId → 未处理
T3  Worker A: 执行业务副作用并 INSERT
T4  Worker B: 也执行业务副作用并 INSERT
```

问题出在 T1/T2 与 T3/T4 之间存在 check-then-act 窗口。解决时不能只“再查仔细一点”，而要把竞争收敛到一个原子点，例如：

```sql
INSERT INTO processed_events(event_id)
VALUES (?)
ON CONFLICT DO NOTHING;
```

并用唯一约束裁决谁成功。后到事务即使自己的快照里没有看到前一个事务，也会在唯一索引写入时发生等待 / 冲突，从而把并发重复收敛为一次成功。

如果副作用和去重记录不在同一个事务边界内，还需要继续分析“去重成功但副作用失败”或“副作用成功但去重未落库”的一致性问题。这是下一层可以继续追问的节点，但当前题的 check-then-act 机制本身已经先解释完整。

## 示例 5：验证题

### 问题：自动化检查全绿，为什么仍可能有用户可见错误？

因为测试只能证明它实际观察到的条件。源码里存在主题变量、DOM shim 生成了节点、CLI 返回 0，都不自动等价于“真实浏览器里用户看到的页面正确”。

可以把测试抽象成：

```text
Input
→ System Under Test
→ Observation Point
→ Assertion
```

假设测试只检查生成的 CSS 里存在：

```css
--brand: ...;
```

即使目标元素从未使用这个变量，静态断言仍会通过，但用户可能看不到任何主题变化。

| 观察层级 | 能证明什么 |
| --- | --- |
| 源码 / 静态生成物 | 预期结构或字符串存在 |
| DOM / Renderer | 页面生成了什么节点和属性 |
| 真实浏览器 | CSS 解析、级联、交互后的实际结果 |
| 打印 / PDF | 最终交付视图是否可读、分页和字体是否正确 |

因此测试结论不能超过输入范围、Observation Point 和 Assertion。若本轮没有真实执行测试，也不能把“仓库定义了这些检查”写成“我刚运行全部通过”。
