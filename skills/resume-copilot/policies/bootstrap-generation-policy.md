# Bootstrap Generation Policy

## 目的

在用户信息很少时也能快速给出可见成果，同时严格控制事实幻觉。

## 可以做

- 根据岗位与关键词决定候选简历区块。
- 归一化技术关键词。
- 将用户原话重写为更简洁的候选表达。
- 根据已明确项目名 / 技术名创建项目占位骨架。
- 标记信息缺口并生成针对性问题。
- 在用户已有明确 Action 时生成弱表述的 provisional bullet。

## 不可以做

- 仅凭技术关键词推断用户实际实现过某方案。
- 自动补充 ownership。
- 自动补充业务背景、架构决策或性能指标。
- 把常见最佳实践写成用户实际经历。
- 从 JD 中复制能力要求并伪装成用户经历。

## 动词强度

信息不足时优先使用低承诺表达：

- 涉及
- 参与
- 围绕
- 使用
- 开展

只有 Ownership 已验证后，才可使用：

- 负责
- 主导
- 设计
- 搭建
- 重构
- 推动

## Placeholder 原则

比起编造事实，优先显式留下可行动缺口：

```text
- [待确认：具体优化动作]
- [待补充：结果指标]
```

但对用户展示时应自然表达，例如：

```text
目前缺少“你具体改了什么”和“最终结果”，补齐这两点后这条项目经历就可以成型。
```

## Target-first + Draft-first 原则

当用户目标是“帮我生成简历”时：

1. 先确认 Target Role / Target Direction。
2. 若未提供，主动询问；不得根据技术栈自动判断方向。
3. 方向明确后，除非完全没有任何职业信息，否则优先先给一个可讨论 Draft，再追问；不要把所有问题问完之后才第一次展示简历。

在 Target Role 未知时，可以整理 Facts 和信息缺口，但不要输出岗位定向的 Resume Bullet。

## Bootstrap Bullet 写作要求

即使是 provisional bullet，也应尽量遵循 `resume-writing-policy.md` 的结构，不要为了“先出结果”输出空泛职责句。

当信息不足以形成“动作 + 对象 + 技术机制”时，宁可输出候选骨架和明确缺口，也不要生成：

> 负责 XX 相关能力建设。

如果已有足够机制信息，可以先生成 provisional 的高信息密度表达；其中尚未验证的 Ownership、Result、Metric 必须保持弱表述或明确待确认。
