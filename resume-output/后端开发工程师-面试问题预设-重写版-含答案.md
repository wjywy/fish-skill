# Node.js CLI：从命令分发到安装一致性

## 你在 fish-skill 里做的 CLI 具体解决什么问题？

**直接回答**

我做的是一个把仓库里的 Skill 分发到当前项目的 Node.js 命令行工具。`list` 发现可安装的 Skill，`check` 做基础入口检查，`install` 把指定 Skill 复制到目标目录；这样使用者不用手工找文件、逐个复制。

**展开说明**

CLI 从 `process.argv` 读取命令。`list` 扫描包内的 `skills/`，把“直接子目录里存在 `SKILL.md`”作为发现条件并排序输出。`check` 复用同一份列表，读取每个 `SKILL.md`，当前只检查内容是否以 `---` 开头。它没有解析完整 YAML，也没有检查所有引用文件，所以我不会把它称为完整的 Skill 校验器。

`install` 先确认 Skill 名称在列表中，再把源目录递归复制到 `--target` 指定的位置；未指定时，目标根目录是当前项目的 `.agents/skills`。递归过程会建目录，对普通文件调用 `copyFileSync`。例如在项目 A 运行 `fish-skill install resume-copilot`，最终会得到 `项目A/.agents/skills/resume-copilot/`。已有同名目录时默认拒绝，只有显式传 `--force` 才会覆盖。

## 既然目标目录按当前工作目录解析，为什么源目录不能也用 `process.cwd()`？

**直接回答**

因为源目录属于 npm 包，目标目录属于运行命令的项目，它们的定位基准不同。我用模块自身的位置找包内 `skills/`，用 `process.cwd()` 解析用户传入的目标路径。

**展开说明**

当前代码把 `import.meta.url` 转成文件路径，再依次取 CLI 所在目录、包根目录和 `skills/`：

```text
import.meta.url → fileURLToPath → dirname → packageRoot → skillsRoot
```

这样无论使用者在哪个目录执行，源文件都跟着已安装的包走。相反，`--target .agents/skills` 表达的是“当前项目里的这个相对位置”，所以用 `path.resolve(process.cwd(), target)` 得到目标根目录。

例如包实际位于 `/opt/fish-skill`，命令在 `/home/me/app` 中执行：源文件是 `/opt/fish-skill/skills/resume-copilot`，目标是 `/home/me/app/.agents/skills/resume-copilot`。如果源也从 `cwd` 推导，CLI 就会错误地去 `/home/me/app/skills` 找包内资源，换一个执行目录就可能失败。

## 目标目录已经存在时，`--force` 到底保证了什么？

**直接回答**

`--force` 保证的是“覆盖必须由使用者明确选择”。它不保证安装原子性，也不保证复制失败后旧版本还能恢复。当前实现遇到已有目录且没有 `--force` 时直接退出；有 `--force` 时先删旧目录，再复制新版。

**展开说明**

当前顺序是：

```text
检查目标是否存在 → 检查 --force → 删除目标 → 递归复制源文件
```

如果旧目录删除后，复制到一半遇到磁盘空间不足或文件系统错误，目标可能只剩一部分新版文件；原有版本也已不在。`--force` 只消除了“未经同意覆盖”的风险，没有为失败恢复提供备份或回滚路径。

因此这里的准确表述是**显式覆盖保护**。若要进一步保证更新期间始终有一套完整文件可用，需要改变写入顺序并定义切换失败后的恢复规则；这不是当前 CLI 已实现的能力。

## 如果要避免覆盖中途留下半套 Skill，你会怎样改？

**直接回答**

如果改造，我会先在同一文件系统的临时目录完整准备新版，校验通过后再切换正式目录，并保留旧版备份直到切换确认成功。这样复制阶段失败不会破坏旧版。

**展开说明**

我会把一次更新拆为三个阶段：

1. **准备**：在目标的同级目录创建唯一的 `temp`，复制完整 Skill，并检查需要的入口文件和文件清单。失败时只删除自己的 `temp`。
2. **切换**：把现有 `target` 重命名为 `backup`，再把 `temp` 重命名为 `target`。临时目录与目标在同一文件系统，才可能利用单次 `rename` 的原子可见性。
3. **清理或恢复**：新版成功占据 `target` 后删除 `backup`；第二次重命名失败时先尝试把 `backup` 恢复为 `target`。

两个 `rename` 仍是两次独立操作，不能宣称整个更新原子。比如进程在 `target → backup` 之后崩溃，下次启动可能看到 `target` 不存在、`backup` 和 `temp` 都存在。恢复程序需要识别这个中间状态，优先恢复旧版或按明确规则继续提交，不能直接清理备份。当前代码尚无临时目录、备份和崩溃恢复协议；这些是改造方案。

## 两个进程同时 `--force` 安装到同一目录，暂存加重命名还够吗？

**直接回答**

不够。独立临时目录只能避免两个进程在准备阶段写到同一位置；提交阶段仍会争用同一个 `target`。如果要支持并发安装，我会对目标路径的提交过程加互斥，并在取得锁后重新读取目标状态。

**展开说明**

假设 A 和 B 都基于旧版 V0 准备了各自的临时目录。A 先把 V0 重命名为备份；此时 B 看到 `target` 暂时不存在，可能以为没有旧版。随后 A 把 VA 切为正式目录，B 再提交 VB，就可能覆盖 A 的结果，甚至把 A 的新版当作待备份旧版。每个临时目录本身都完整，最终结果仍可能不符合任一进程最初观察到的状态。

关键是把“重新检查目标 → 备份 → 切换 → 确认提交”放进同一个**目标路径级临界区**。复制新版可以在锁外完成，减少锁占用；拿到锁后必须重新检查目标版本和备份状态，再决定提交或终止。锁还要有异常退出后的回收规则，不能让一次崩溃永久阻止后续安装。

也可以记录目标版本或文件摘要，准备时记下 V0，提交时要求目标仍为 V0。但普通的“读摘要 → 判断 → 重命名”仍有竞态；版本判断和提交需要锁或其他真正的原子条件配合。当前 CLI 没有这些并发控制措施。

# 简历事实模型：从仓库证据到可追溯表述

## 你说设计了 `Fact → Experience → Claim → Resume View`，每一层负责什么？

**直接回答**

我用这几层把“材料里有什么”“我实际做了什么”“最终能怎样写”分开。`Fact` 记录来源明确的事实，`Experience` 组织一次项目经历，`Claim` 表示有事实支撑、可以对外主张的能力或成果，`Resume View` 再按目标岗位挑选和呈现 Claim。

**展开说明**

以这份简历里的 CLI 描述为例，仓库代码可以形成一个项目事实：项目存在 `list/check/install` 功能；用户确认“整个项目由我完成”是另一条人物事实。`Experience` 把这些事实放进 `fish-skill` 这个项目的时间、目标和行动上下文。`Claim` 同时引用项目功能与个人贡献事实，才可以写出“独立开发 Node.js CLI”。

`Resume View` 中的那条 bullet 引用 `claim-cli`，决定它在后端岗位简历里怎样呈现。岗位选材还经过 `Resume Strategy`：它筛选与目标岗位相关的 Claim，但不能创造新事实。所以这条链路的职责可以理解为：**Fact 管依据，Experience 管上下文，Claim 管可主张的表述，Strategy 与 View 管选择和展示**。

把它们拆开后，修改一条简历句子时可以反向查看支撑事实；切换目标岗位时也能重新组合已有 Claim，而不必从一篇自由文本里重新猜测哪些内容真实。

## 既然代码都在仓库里，为什么还要单独确认“是你做的”？

**直接回答**

仓库能证明一个功能存在，不能单凭功能代码证明由谁完成。我在模型里把仓库提取的 `PROJECT` 事实与用户确认的 `USER` 贡献事实分开；写“独立开发”时需要后者。

**展开说明**

看到 `bin/fish-skill.mjs` 中的 `install`，可以确认项目实现了安装命令。可是同一份代码可能来自多人协作、复制的样例或他人的提交；即使有 Git 作者信息，也可能存在代提交、结对编程或 squash。代码本身无法给“独立开发”盖章。

在当前资料里，仓库事实 `fact-cli` 说明功能实现，用户在对话中确认整个 `fish-skill` 由本人完成，形成 `fact-owner`。`claim-cli` 同时引用这两条事实，才支撑简历中的“独立开发”。如果只有 `fact-cli`，我仍可以介绍项目具有什么能力，但不能把它自动升级成个人主导经历。

这种区分也适用于指标：测试输出可证明当前运行通过了多少断言，却不能据此推导“线上稳定性提升”或“节省多少人力”。不同主张需要不同来源的证据。

## 一条简历描述怎样回溯到具体证据？

**直接回答**

我从最终 bullet 的 `claimIds` 开始，找到对应 Claim，再沿 Claim 的 `factIds` 找到事实及其来源。数字还要沿 `metricIds → Metric → factIds` 单独追溯。这样可以检查一句话的每一部分由什么支撑。

**展开说明**

例如简历里“独立开发 Node.js CLI……”这条 bullet 的 ID 是 `bullet-cli`，它引用 `claim-cli`。`claim-cli` 又引用 `fact-cli` 和 `fact-owner`：前者定位到 CLI 代码和包配置，证明功能确实存在；后者来自用户确认，支撑“独立开发”这个 ownership 用词。

```text
bullet-cli → claim-cli → fact-cli   → bin/fish-skill.mjs / package.json
                      → fact-owner → 用户对个人贡献的确认
```

“78 项检查通过”是带数字的另一条 bullet。它除了引用 `claim-tests`，还通过 `metric-checks` 关联到 `fact-tests`，数字的范围是当前 `npm test` 测试集合。若测试集合改变，不能只改文案里的数字，还要重验 Metric 的来源与口径。

实现这种回溯时，我会先建 Fact、Claim、Metric、Experience 的 ID 索引，再逐段遍历引用；遇到缺失 ID 直接报出具体 bullet 与字段。当前仓库的确定性测试已经做了**引用 ID 是否存在**的检查，但它还不能自动判断“这条事实在语义上是否足以支撑这句话”。后者仍要看事实内容和证据规则。

## JSON Schema 已经规定字段了，为什么还需要额外的证据规则和引用检查？

**直接回答**

JSON Schema 管数据形状，例如字段类型、必填项和枚举；引用检查管对象之间的关系；证据规则管一句话能否由这些事实推出。三层检查回答的问题不同，不能相互替代。

**展开说明**

Schema 可以规定 `claimIds` 必须是非空字符串数组，但即便有 `"claimIds": ["claim-does-not-exist"]`，它的形状仍然正确。跨对象校验需要拿这个 ID 去 Claims 集合查找；当前 `T3` 测试对 Claim、Fact、Metric、Experience 和 View 的若干引用执行了这类存在性检查。

再进一步，`claim-cli` 即使确实存在、`fact-cli` 也能找到，仍要判断引用**是否有证明力**：仓库里的 CLI 代码可以支撑“项目实现了 install”，却无法独自支撑“我独立实现了 install”。这时必须结合 `fact-owner`。同理，一个 78 项的测试计数并不能证明 78% 覆盖率。

所以我会按顺序检查：

1. 对象能否通过 Schema，避免字段缺失或类型错误。
2. 所有引用 ID 是否存在，并且是否连接到正确的项目或经历。
3. 来源与 ownership 是否足以支撑最终 Claim，指标是否有明确口径。

当前测试对第一层和部分第二层有机械覆盖；第三层主要依赖事实政策与人工判断。若把“ID 存在”当作“表述可信”，系统仍可能生成结构正确但内容失真的简历。

# Resume View 到 HTML：生成、渲染和安全边界

## 从一份 Resume View JSON 到能打开的简历页面，中间发生了什么？

**直接回答**

我用 `build-resume.mjs` 读取 Resume View JSON，组装样式、数据和浏览器端渲染器，再写出 HTML。默认画廊模式会生成一个主题入口页和五个使用同一份简历数据的主题页；指定主题时也能生成单文件页面。

**展开说明**

命令先解析 `--data`、`--theme`、`--mode`、`--out` 等参数，读取 JSON 并执行 `JSON.parse`。目前生成脚本只做了 `header` 是否存在的入口检查，**没有在生成前对整份 Resume View 运行 JSON Schema 校验**。这一点和测试套件对样例数据做 Schema 校验是两回事。

接着脚本从模板目录读取上游 Kami 样式、本项目的布局覆盖层和 `kami-render.js`。在默认 `gallery` 模式下，它为 `kami-base/mono/navy/copper/seal` 分别生成成品 HTML，每个页面嵌入相同的 JSON 与渲染脚本，只换主题变量；入口页 `index.html` 提供五个跳转卡片。指定主题的 `single` 模式把 CSS 与 JS 内联到一份 HTML；`linked` 模式则引用相对路径的共享资源。

浏览器打开主题页后，内嵌数据被赋给 `window.KAMI_RESUME_DATA`，脚本调用 `renderKamiResume({ target: "#kami-root", data: ... })`。渲染器按 `header → skills → sections` 的顺序生成 DOM 字符串并写入目标元素。最后导出 PDF 仍通过浏览器打印完成，生成脚本自身不直接排版或输出 PDF。

## 数据直接嵌进 `<script>` 里，怎样避免简历文本提前结束脚本？

**直接回答**

`JSON.stringify` 只保证数据能表示为 JSON，并不处理 HTML 解析器的 `</script>` 结束标签。我在把 JSON 放进脚本前，将每个 `</` 替换成 `<\/`，防止简历文本提前关闭当前脚本。

**展开说明**

假设简历里的项目描述包含 `</script><script>alert(1)</script>`。即使它在 JavaScript 里位于 JSON 字符串内部，浏览器的 HTML 解析器仍会先识别 `</script>`，结束当前脚本；后面的内容就不再处于原本的数据字符串中。`JSON.stringify` 对引号、反斜杠等 JSON 字符负责，却不会自动处理这种 HTML 容器边界。

当前 `safeJson` 的处理结果会把输入中的 `</script>` 变成 `<\/script>`。HTML 解析器看不到连续的 `</script>`，而 JavaScript 解析字符串时又会把 `\/` 还原为普通斜杠，数据内容保持原意。脚本还用 `safeInline` 处理内联的渲染器代码中可能出现的闭合标签。

这一步只保护**嵌在 script 内的 JSON 与脚本内容**，不等于整页所有插入位置都已经安全处理。随后把数据写进 DOM 时，还要根据它进入文本、HTML 属性还是链接地址，分别应用相应规则。

## 数据到了渲染器之后，普通文本、强调标记和链接分别怎么处理？

**直接回答**

普通文本先做 HTML 特殊字符转义；描述里的 `**关键词**` 在转义后再转换为强调样式；链接则既要处理属性里的字符，也要判断地址是否允许跳转。当前渲染器完成了前两件事，但链接地址的协议校验还不完整。

**展开说明**

`esc()` 会把 `& < > " '` 转成 HTML 实体，所以像 `<script>` 这样的姓名或描述内容只会显示为文字，不会变成标签。`inline()` 先调用 `esc()`，然后才把 `**Node.js**` 转成 `<span class="hl">Node.js</span>`。先转义再识别受控标记，能防止输入中的任意 HTML 借强调语法进入页面。

链接是另一种上下文。`entry.link` 与 `contact.href` 会被转义后写入 `href`；`entry.meta` 只有以 `http://` 或 `https://` 开头时才按链接渲染，否则按普通文本处理。但前两类链接当前没有统一的 `http/https` 协议白名单：属性转义能挡住引号破坏标签结构，却不能保证 `javascript:` 一类地址是安全的。

如果完善这部分，我会先用 URL 解析并校验协议，只接受预期的 `https:`、必要时的 `http:` 或明确支持的 `mailto:`；不通过的值作为纯文本显示。校验后仍要保留属性转义，因为协议安全和 HTML 语法安全解决的是不同问题。

## 五套主题为什么能共用同一份简历数据？

**直接回答**

因为内容结构与视觉配色分开了。同一份 Resume View 交给同一个 `kami-render.js` 渲染；主题只覆盖一组 CSS 颜色变量，不改 Claim、bullet 或 DOM 映射。

**展开说明**

基础版式来自 `kami-family.css`，页头等本项目调整写在 `kami-layout.css`。五套主题是 base、mono、navy、copper、seal；主题页通过 `--parchment`、`--brand`、`--stone` 等变量控制纸色、强调色与文字层级。生成器每次读取同一份 JSON，只替换色板声明，因此五份 HTML 的项目内容一致。

这个分离的前提是渲染器输出的类名与样式规则保持一致。例如 bullet 被映射成 `.proj-row`，强调词被映射成 `.hl`；CSS 变量改变它们的颜色，而不会改变内容字段。如果主题页缺少对应声明，或者声明没有被实际选择器使用，虽然 HTML 可以生成，视觉上仍可能没有差异。仓库目前有静态的主题变量与对比度检查；要证明用户实际看到五种颜色，还应在浏览器中读取关键元素的计算样式。

## 单文件页面为什么仍可能在离线打印 PDF 时出问题？

**直接回答**

“单文件”只表示主要 HTML、CSS、JavaScript 和简历数据放在同一个文件里，不保证所有运行时资源都离线可用。这个项目保留了 `@font-face` 的本地路径和 CDN 回退；离线机器如果找不到字体，浏览器就会用替代字体，打印版式也可能变化。

**展开说明**

生成器在 `single` 模式会内联 CSS 和渲染器代码，但没有把字体二进制塞进 HTML。浏览器解析 `@font-face` 时仍按字体源列表查找：本机字体、本地文件路径、远端 CDN。离线且本地字体不存在时，CDN 访问失败，页面通常不会空白，而是退回系统字体。字体宽度、行高不同，可能让原来刚好一页的内容换行或分页，甚至影响中文文字在 PDF 中的显示和搜索体验。

打印还有浏览器设置这一层。主题纸色依赖背景颜色，用户如果关闭“打印背景图形”，导出的 PDF 可能与屏幕预览不同；不同浏览器的分页和字体加载时机也会影响结果。因此交付前应在目标环境确认字体已加载，再用浏览器实际打印检查页数、换行和背景色。仓库提供 `ensure-fonts.sh` 辅助准备字体，但脚本存在不代表每台离线机器都已经安装成功。

# 自动化测试：78 项检查能证明什么

## 简历里写“78 项确定性检查通过”，具体指哪些检查？

**直接回答**

这个数字来自当前仓库执行 `npm test` 的结果：测试脚本登记的 78 项确定性检查全部通过。它覆盖包结构、Schema 样例、对象引用、渲染器、CLI、文档契约和简历内容规则；它不是代码覆盖率，也不是生产稳定性指标。

**展开说明**

`npm test` 调用 `node test/run-tests.mjs`。当前七组检查的数量分别是：包与结构 14 项、JSON Schema 13 项、跨对象引用 5 项、Kami 渲染器契约 20 项、CLI 10 项、内部规范一致性 10 项、简历内容 lint 6 项，加起来是 78。它们都以可重复断言的通过或失败为结果；我在当前工作区重新运行，得到 `78/78 checks passed`。

例如，CLI 组会真的执行 `install`，断言目标目录里出现 `SKILL.md`；引用组检查 bullet 的 `claimIds` 是否能找到；渲染器组检查转义后的 HTML、主题类名和页头结构。这些检查的粒度不同，不能把“78 项”解释成“78 个完整用户场景”。

如果以后拆分或增加断言，数字会变化，即使产品能力完全没变。所以我会把这个指标限定为**当前版本的测试集合通过数**。它能说明仓库定义的这些契约现在没有被检测出违反，不能替代真实浏览器、打印环境或更大范围的系统测试。

## 为什么 Schema 测试要同时准备合法和非法样例？

**直接回答**

合法样例验证规则没有误伤应该接受的数据；非法样例验证关键约束确实会拒绝错误数据。只测一种方向，容易出现“规则太严”或“规则根本没生效”却仍然全绿。

**展开说明**

仓库的 `T2` 把 Career Profile、Resume View、Strategy 等合法样例送进校验器，要求错误列表为空；同时准备缺失 `statement`、错误枚举、空 `factIds`、bullet 缺 `claimIds` 等非法样例，要求返回错误，并且错误路径或文本指向预期字段。

假如 `claimIds` 本应非空，某次修改意外去掉了 `minItems`：合法样例依旧能通过，但 `claim-empty-factids` 这类负例会暴露“错误数据也通过”的问题。反过来，如果把可选字段误设为必填，负例仍可能被拒绝，合法样例却会失败。

这里的校验器是仓库实现的**JSON Schema 子集**，支持当前文件用到的 `type`、`required`、`enum`、`$ref` 等关键字，不等同于完整通用的 JSON Schema 实现。正反例证明的是这些已覆盖规则在当前样例上的行为，不意味着所有标准特性或任意输入都已测试。

## 引用完整性为什么不能只靠 JSON Schema 测试覆盖？

**直接回答**

Schema 能要求引用字段存在、类型正确，却通常不知道另一个对象集合里有哪些 ID。要确认一条 bullet 引用的 Claim、Claim 引用的 Fact 确实存在，需要把整份数据放在一起做跨对象检查。

**展开说明**

例如 `"claimIds": ["claim-404"]` 是一个非空字符串数组，可以符合 Resume View Schema，但如果 Career Profile 的 `claims` 中没有 `claim-404`，这条简历描述就无法追溯。`T3` 因而先把 Fact、Claim、Metric、Experience 的 ID 收集成集合，再遍历 Claim 的 `factIds`、Metric 的 `factIds`、View bullet 的 `claimIds/metricIds` 等引用。查不到时，错误会指出来源对象与缺失 ID。

当前实现主要检查**引用是否存在**，并另有少量 Strategy 选择与 Metric 状态相关断言；它没有自动证明“两个存在的 ID 在业务语义上属于同一段经历”，更不能证明 Fact 本身真实。若要加强，校验器还需比较 `experienceId`、Claim 的事实类别和 Metric 的范围，再把证据政策接入审核流程。这样才能从“不会悬空”走向“引用关系合理”。

## CLI 会读写目录，怎么让安装测试既真实又可重复？

**直接回答**

我让测试在系统临时目录里真正启动 CLI 子进程并执行安装，再检查退出码和实际文件。每次测试创建独立目标目录，所以不会覆盖开发者的项目，也不会依赖上一次运行留下的安装结果。

**展开说明**

`T5` 使用 `mkdtempSync(os.tmpdir())` 创建唯一目录，然后通过 `execFileSync('node', [BIN, ...args])` 运行真实入口。正常安装后，测试检查目标 `SKILL.md`、各子目录和复制前后的文件数量；接着覆盖场景分别验证“不带 `--force` 拒绝”和“带 `--force` 成功”。未知 Skill、未知命令也验证非零退出码和错误信息。

这种方式让文件系统行为真实发生，同时把写入范围限制在临时目录。它与只 mock `fs.copyFileSync` 不同：实际路径解析、建目录、复制和命令退出都会经过真实代码。为了提高失败路径的可信度，我还会补一个故障注入或权限失败场景：先在旧目录写入哨兵文件，触发安装失败后比较哨兵字节内容，明确验证旧版是否仍完整。当前测试覆盖了正常与显式覆盖路径，**没有**证明复制中途失败可恢复。

## 渲染器测试用了模拟 DOM，它与真实浏览器验证有什么差别？

**直接回答**

模拟 DOM 让我能快速检查渲染器生成了什么 HTML 字符串，以及转义、字段映射等确定性逻辑；但它不解析 CSS、不计算布局，也不执行真实打印。因此它不能证明用户打开页面后的颜色、分页和交互都正确。

**展开说明**

仓库的 `dom-shim.mjs` 只提供渲染器需要的少量接口：`document.body`、`querySelector`、`classList` 和 `innerHTML`。测试加载真实的 `kami-render.js`，把 Resume View 交给它，再比较生成的字符串。这适合断言“姓名被 HTML 转义”“bullet 被放进 `.proj-row`”“有头像时输出 `img.avatar`”等行为，执行也快而稳定。

真实浏览器还会经历 HTML 解析、CSS 层叠、字体加载、布局、事件处理和打印。比如 CSS 中定义了 `--brand`，静态测试可以确认变量存在，却未必证明目标元素的 computed style 真变了；模拟 DOM 也无法发现字体加载失败导致的换行变化。要验证这些结果，需要打开生成的 HTML，在浏览器里检查关键元素计算样式、链接实际跳转、头像交互和 PDF 打印结果。

这两层验证解决的问题不同：模拟 DOM 守住渲染函数的稳定契约，浏览器验证守住用户实际看到和操作到的结果。
