以下问答以**后端开发工程师**为目标方向，以 `fish-skill` 0.1.19 的当前项目实现为场景。代码能证明项目怎样工作，不能据此认定某项工作由我独立完成。涉及尚未实现的方案时，答案会明确使用假设语气。

# Skill 安装链路的路径与更新一致性

## npm 包安装在任意位置时，CLI 为什么仍能找到 Skill？

因为包内资源以**入口脚本的位置**定位，而安装目的地以**调用者的工作目录**定位。当前入口把 `import.meta.url` 转为本地文件路径，向上找到包根，再读取其 `skills/`；执行 `install` 时，目标根目录则由 `process.cwd()` 加上 `--target` 得到，默认是调用项目下的 `.agents/skills`。

例如包在 `/opt/fish-skill`，调用者位于 `/home/dev/app`：源目录是 `/opt/fish-skill/skills/resume-copilot`，默认目标是 `/home/dev/app/.agents/skills/resume-copilot`。如果两者都依赖工作目录，CLI 会误把调用项目当作自己的资源目录；如果两者都依赖脚本目录，Skill 又会装回 npm 包里。这里的关键区别是**模块相对资源**与**调用者相对输出**。

`list` 枚举包内带 `SKILL.md` 的直接子目录；`check` 读取这些入口，但目前只检查文本是否以 `---` 开头。它能发现缺少 frontmatter 起始标记，不能证明 YAML 内容、内部引用和实际运行都正确。完整性需要更具体的校验或测试。

## 目标目录已存在时，`--force` 到底解决了什么？

它只解决**覆盖授权**：目标已存在时，未传 `--force` 就拒绝；传入后允许替换。当前实现的替换顺序是删除旧目录，再递归复制包内目录，所以没有失败回滚，也没有整次安装的原子可见性。

```text
目标存在 → 无 --force：退出，旧目录保留
目标存在 → 有 --force：删除旧目录 → 逐项复制新版
```

假设复制到一半磁盘写满，旧版已经被删除，新版可能只有部分文件；另一个进程在此期间读取，也可能看到目录短暂缺失或内容不完整。这说明“用户允许覆盖”与“覆盖后始终有一版可用”是两项独立要求。若测试只断言带 `--force` 的正常安装成功，仍覆盖不到这个失败窗口。

## 如果复制中途失败，怎样让旧版仍可恢复？

如果改造，我会把更新拆成**准备、切换、恢复**三个阶段。先在正式目录旁的同一文件系统创建唯一暂存目录，完整复制并校验；准备失败只清理暂存目录，旧版仍留在正式路径。准备成功后再把旧版移到备份路径，把暂存目录改名为正式路径。

```text
准备：target=旧版，temp=新版候选
切换 1：target → backup
切换 2：temp → target
收尾：确认新版可用后清理 backup
```

单次同文件系统 `rename` 通常能让读者看到完整目录名变更，但上面的两次 `rename` **合起来不是一个原子操作**。进程若在两次之间崩溃，会留下 `target` 缺失、`backup` 与 `temp` 同在的状态；重启时应识别并优先恢复备份，而不是把残留目录一律删除。若第二次改名失败，同样要先恢复旧版。这个方案缩小了不完整文件暴露的范围，却仍需要定义切换空窗与断电持久化要求；当前 CLI 尚未实现这些步骤。

## 两个进程各自使用唯一暂存目录，为什么正式目录仍会竞争？

唯一暂存目录只能避免**准备阶段互相写坏文件**，不能决定谁有权提交到同一个正式路径。假设 A、B 都从旧版 V0 开始准备新目录 VA、VB：

```text
A：准备 VA                    B：准备 VB
A：把 target(V0) 移到 backup-A
                              B：看到 target 缺失，认为可首次安装
B：把 VB 改名为 target
A：再提交 VA，遇到冲突或误入恢复分支
```

竞态发生在“检查正式目录状态”与“提交改名”之间。可靠更新需要在**正式目标**上仲裁：一种做法是跨进程锁覆盖检查、备份、切换和提交确认，并在取得锁后重新读取状态；另一种做法是由存储系统提供真正的原子条件提交。仅在锁外先读版本号，再执行普通改名，仍会留下先查后改的窗口。当前安装器没有这类协调，因此并发安装同一目标并无完整结果保证。

## 若改用有过期时间的锁，旧持锁进程醒来后会有什么风险？

租约到期只说明新进程**可以取得锁**，不保证旧进程已经停止。A 持锁后暂停，租约到期；B 取得新锁并写入 VB；A 恢复后若仍能提交 VA，就会把 B 的结果覆盖。这个风险叫过期持有者写入，不靠给租约设置更长时间就能消除。

若选择租约协议，提交目标必须能原子比较一个递增的代际或 fencing token：B 持有更高代际，存储层拒绝 A 的旧代际写入。仅把 token 放在进程内检查，仍有“检查后、写入前”的竞态；普通文件系统重命名也不会自动识别 token。对这个本地 CLI，先采用随进程退出释放的系统级互斥并在锁内重新检查，通常比自行设计可过期租约更直接。两者都只是改造方向，当前代码没有实现锁。

# 从项目事实到可信简历表述

## 为什么不能把仓库里看到的功能直接写成个人简历 bullet？

因为“项目具有某能力”和“某人以某种程度完成该能力”是两个不同命题。仓库代码可以支持前者；后者还要核实个人的动作、决策和责任范围。Resume Copilot 用 Fact 保存来源事实，用 Experience 组织项目上下文，用 Claim 表述可主张的贡献，再由 Strategy 选择、Resume View 展示，Renderer 只负责视觉输出。

以安装命令为例：代码可形成“项目支持复制安装 Skill”的**项目事实**。如果用户确认自己编写了安装逻辑，才能再形成“本人直接实现该逻辑”的**人物事实**；若只是参与评审，动词应落在“参与评审”而不是“独立开发”。Claim 引用支撑它的 Fact，bullet 再引用 Claim。换一个目标岗位时，可以调整选材与措辞，但不应悄悄改写底层事实。

这套分层的理由是让**来源、解释、主张、呈现**各自可检查。若直接从代码生成“我主导了完整系统”，既跳过 Ownership 验证，也无法解释这句话中“主导”的证据来自哪里。当前仓库定义了这些模型和引用字段；仅凭本仓库，仍不能判定用户的实际贡献。

## Schema 已要求 bullet 引用 Claim，为什么还需要别的校验？

Schema 只能确认**结构合法**；随后还要确认**引用存在且归属正确**，最后确认**证据足以支撑语义**。这三层不能互相替代。

| 层次 | 典型检查 | 即使通过仍可能错在哪里 |
| --- | --- | --- |
| 结构 | `claimIds` 是非空字符串数组 | 引用的 Claim 根本不存在 |
| 引用 | bullet → Claim → Fact 都能解析 | Claim 的事实只证明项目功能，不证明个人主导 |
| 语义 | 动词、范围、数字与来源相称 | 用户可能仍无法解释未亲历的实现细节 |

例如 `claimIds: ["claim-a"]` 在字段类型上可以合法，但 Profile 中若没有 `claim-a`，链就断了。补上同名 Claim 后，如果它仅引用 REPOSITORY 来源的项目 Fact，bullet 仍不能写“我独立设计”。当前测试会核对内置示例和 fixture 的多种 ID 关系，也检查样例 bullet 带 Claim 引用；它并未为任意用户材料自动判定 Ownership 语义。`$ref` 复用 JSON Schema 定义，不是业务对象的外键查询。

## 若要检查整条引用链，怎样让报错指向真正的问题？

如果实现通用校验器，我会先为 Fact、Experience、Claim、Metric 和 Strategy 建立按类型分开的 ID 索引，建索引时拒绝重复 ID；再从每条 bullet 反向走到 Claim、Fact 与 Metric。遍历要带上当前位置，错误才能落到某条经历的某个 bullet，而非只给出“Profile 不合法”。

检查顺序是：先验证 bullet 引用的 Claim 是否存在、是否被当前 Strategy 选中；再验证 Claim 所属 Experience 及 `factIds`；遇到数字时核对 Metric 的来源和 Experience 归属。假设一条项目经历的 bullet 引用了另一段经历的 Metric：所有 ID 都存在，普通集合查找会放行，但作用域已经错了。若 Claim 写“独立负责”，事实却只有项目代码，则是另一种**证明范围**错误。

当前 T3 针对固定样本做了引用存在性和选材检查；重复 ID、跨经历归属与措辞证据的完整判断属于进一步设计。这样的校验器应输出类似“第 2 段经历、第 3 条 bullet 引用了另一段经历的指标”的定位信息，并保留原始来源，方便修正事实或文案。

## 提交记录能把“项目做了什么”升级成“我主导了什么”吗？

不能自动升级。提交记录能帮助定位某次修改的作者、时间和变更范围，却不能单独证明需求是谁定义、方案是谁决定、关键部分是谁实现、最终责任由谁承担。结对编程、代提交、合并压缩以及后续重构都会让“提交者”与实际贡献范围不完全一致。

例如某个 commit 改了安装命令，可以进一步核对 PR 讨论、评审和用户的具体描述：本人写了复制逻辑，还是只修了报错文案？若只确认直接实现了一个模块，Claim 可以写“实现安装命令的目标路径解析”；若要写“主导 Skill 分发体系”，还要有方案与责任范围的证据。Ownership 与证据强度分开判断：来源可靠的代码事实仍可能只支持项目能力，不能替代人物事实。

## 指标已经出现在材料里，何时可以写进简历？

要先确认**值代表什么、怎样取得、比较口径是否一致、是否允许写入**。当前 Metric 模型独立保存数值、单位、范围、来源关联和确认状态；默认只有已确认且可用于简历的指标，才可以作为确定数字进入 bullet。一个数值即使在仓库里出现，也可能只是测试 fixture、配置上限或局部 benchmark，不等于生产效果。

假设材料说“某流程从七小时以上降到约五分钟”。可保留前后原始值、统计范围与“约”的不确定性，写作时也保留这些限定；不能自行算出一个精确提升百分比，更不能把一次实验写成全量线上结果。若只有“提升很多”，没有基线和口径，就暂不生成数字。这样做的核心是让面试追问“怎么算的、测了哪些场景”时，能回到真实来源，而不是回到一句经过润色的文案。

# Resume View 到 HTML 的构建与安全边界

## 输入 JSON 怎样变成五套可以打印的简历页面？

构建脚本先读取 Resume View，再装配公共 CSS、版式覆盖、主题色板与浏览器 Renderer；浏览器执行 Renderer 后，才得到实际的简历 DOM。默认未指定主题时，脚本生成画廊入口与五个主题成品页；指定 `--theme` 时默认生成该主题的单文件页面。还有把五套色板放在一页内切换的 `portal` 模式，以及相对引用共享资源的 `linked` 模式。

具体数据流是：`--data` 指向的文件被 `JSON.parse`；脚本目前只检查存在 `header`，**没有在构建阶段运行完整 Resume View Schema**。随后数据被写入页面的 `window.KAMI_RESUME_DATA`，Renderer 把页头、技能、经历和 bullet 映射成 DOM。CSS 的加载顺序让版式覆盖与主题变量作用在公共样式之后；`header.avatar` 决定是否渲染头像布局。最后由浏览器排版并通过打印生成 PDF。

因此，“构建命令成功”只证明这次输入走完了当前 HTML 生成路径，不能推出每个 Claim 引用都真实、浏览器中的视觉效果正确，或 PDF 字体可搜索。内容可信、HTML 可生成、浏览器可见、打印可交付是连续但不同的观察层。

## `JSON.stringify` 的结果已经合法，为何仍要处理 `</script>`？

因为这份数据有**两层解析器**：先被 HTML 解析器当作 `<script>` 内的原始文本扫描，随后才交给 JavaScript。`JSON.stringify` 只保证 JSON 字符串格式；若数据中含 `</script>`，HTML 解析器会先结束脚本标签，根本不会等 JavaScript 判断这些字符是否在字符串内。

```html
<script>
window.KAMI_RESUME_DATA = {"name":"</script><script>...</script>"};
</script>
```

当前脚本的 `safeJson` 把序列化结果中的 `</` 写成 `<\/`。这样 HTML 阶段不再看到原始关闭标签，JavaScript 读取字符串时仍能得到斜杠；内联 Renderer 源码另经过 `safeInline` 处理。这个措施解决的是**数据放进 script 容器**时的边界，不能代替整页的上下文编码。当前页面的 `<title>`、author 元信息和包含头像地址的 HTML 注释还有直接插值；若接收不可信输入，这些位置也应分别按文本、属性与注释上下文处理。

## 文本经过 HTML 转义，为什么 `href` 还可能不安全？

转义与 URL 校验回答的是不同问题。Renderer 的 `esc()` 把 `<`、引号等特殊字符变成实体，防止文本或属性值突破 HTML 语法；但 `href="javascript:..."` 即使引号完整，仍可能让点击触发脚本导航。判断链接能否访问，要另查 URL 的协议与用途。

当前正文会先转义，再将 `**关键词**` 转成受控的强调元素，原始 HTML 因而不会直接变成标签。条目 `meta` 只有看起来以 `http://` 或 `https://` 开头时才渲染为链接；条目 `link` 与联系人 `href` 则直接作为链接属性输出，虽然属性值经过 HTML 转义，却没有统一的协议白名单。比如 `link` 若是 `javascript:alert(1)`，HTML 转义不会改变它的协议。

如果改造，应按字段定义允许的协议：项目地址只接收解析后的 `http:` / `https:`，邮箱和电话字段分别按需要接收 `mailto:`、`tel:`；无效值拒绝或降级为普通文本。协议校验后仍保留属性转义。这样把“字符串不会破坏 HTML”与“浏览器允许怎样导航”分别落实。

## 主题文件和静态测试都通过，如何证明用户真看到了五种配色？

要把声明落到用户可观察的层级。静态检查能证明主题文件存在、颜色变量齐全，生成物检查能证明页面包含色板；**实际看到不同主题**还需浏览器解析 CSS、完成级联后，关键元素的计算样式确实不同。页面打印成 PDF 时，又多了背景色保留、分页和字体的要求。

一个最小验证是用同一份 Resume View 生成五页，分别在浏览器读取强调文字和纸张背景的 `getComputedStyle`，确认不同主题的预期变量真正被元素使用；对 `portal` 模式则点击切换器，确认 `data-theme` 改变后同一内容换色。只查 CSS 中存在 `--brand` 不够：若目标规则没使用这个变量，或者被更高优先级样式覆盖，静态检查仍会通过。

当前测试覆盖五套资源、色板对齐与部分对比度约束；本轮没有执行浏览器视觉或 PDF 检查。因此本题中的浏览器与打印步骤是**验证设计**，不是本轮已取得的实测结果。

# 自动化检查能证明到哪一层

## 本轮“测试全绿”具体指什么，不能推出什么？

本轮在当前仓库执行 `npm test`，确定性检查为 **78/78**，架构契约检查为 **19/19**。前者覆盖包资源、Schema 样本、固定引用关系、Renderer 合同、CLI、内部规范和文案 lint；后者核对 Skill 各层职责与面试流程的不变量。这说明**本轮这些输入在这些断言下通过**，不是“任何简历输入、浏览器或打印环境都正确”。

例如 CLI 组真正启动安装命令并检查复制与覆盖路径；引用组主要核对仓库内的示例和 fixture；Renderer 组以 DOM 合同与静态资源为主要观察点。它们的证据强度不同：给定 fixture 的 ID 完整，不意味着新用户的 Profile 自动可信；CSS 变量存在，也不意味着真实浏览器的每个元素都使用了它。写测试结论时要同时指出**输入、观察点、断言与结论边界**。

本轮还从发布包安装了 0.1.19 的 Skill，并用安装后的脚本生成一个单主题 HTML；这证明了安装到静态 HTML 生成的路径可运行。它没有替代浏览器交互或 PDF 检查，也不增加任何个人项目 Ownership 证明。

## 文档相对路径检查通过了，为什么仍需理解它的误报与漏报边界？

因为当前 T6.1 用文本规则找“反引号包住、后缀像资源文件”的字符串，再尝试在文档邻近位置、Skill 根目录或 Skill 树中按唯一文件名解析。这能发现不少坏引用，但它理解的是**字符串形状**，不是作者在句子里表达的意图。

例如文档用反引号举例写一个并非 Skill 资源的 `example.json`，检查器可能把它当作必需文件而误报；反过来，一个普通 Markdown 链接若不符合提取规则，可能不会进入检查。按唯一文件名兜底还可能让“路径写错但别处碰巧存在同名文件”的引用通过。遇到红灯时，应先回到原文看它是实际资源引用还是例子，再核对解析算法与打包内容；不能只凭报错判定资源缺失，也不能未经修正就把失败算作通过。

本轮 T6.1 实际通过。上述例子是在说明静态规则的证明边界，不是声称本轮发生了这些错误。

## 怎样避免测试把实现中的错误假设又写进期望值？

把期望从**用户可观察的需求**推导，而不是从被测实现取值后再与自己比较。比如“未授权不得覆盖已有 Skill”的验收，应先在目标目录放入哨兵文件，再执行无 `--force` 的安装，确认命令拒绝且哨兵内容不变；仅检查错误文案包含“已存在”，不足以证明目录没有被修改。

再看主题：若测试从 CSS 里读出 `--brand`，然后只断言生成物含同一字符串，错误的色值也会随实现一起通过。独立期望应来自预先定义的主题色、关键元素的计算样式和最低对比度要求。必要时做受控变异：故意让安装目标改为包目录、删掉一个主题变量引用，观察对应测试是否转红。若变异后仍全绿，说明该断言没有真正守住需求。

这类设计把“测试数量”还原成“错误能否被观测”。同一个测试可以有很多断言，但若输入从未覆盖失败场景，或观察点与用户实际结果隔了一层，仍会留下空白。

## 只做一条最短端到端验证，应该怎样选关口？

我会选一份含 Claim 引用、强调文本、合法项目链接和头像可选项的 Resume View，依次经过：事实与引用核对、从发布包安装 Skill、用**安装后的脚本**生成 HTML、浏览器查看实际 DOM 与计算样式、打印成 PDF 并检查分页和可提取文本。每一关都只选足以暴露本层错误的观察点：引用关查悬空与 Ownership，安装关查完整文件树，浏览器关查可见内容与导航，PDF 关查最终交付。

本轮实际完成了其中的安装和 HTML 生成：0.1.19 发布包可安装，安装后的脚本用有效 fixture 生成了 `kami-navy` 单文件页面，生成物含数据脚本和 Renderer 调用。`npm test` 也在本轮通过 **78/78 + 19/19**。本轮未打开真实浏览器或打印 PDF，亦未验证任意真实用户 Profile 的人物贡献；因此当前可报告的是**发布包安装到静态页面生成可跑通**，完整端到端交付仍需后续这些观察点。
